# Contributing to MineCode

Keep improvements useful, focused and easy for a small community to maintain. The main repository is maintenance-focused: major defects, security issues and broken installation take priority over new features. Independent forks and continued community development are encouraged. Star the project if it helps you, credit MineCode and retain required notices. Review and maintenance are best-effort; submitting a change does not guarantee acceptance or a support schedule.

## Set up development

Use Python 3.11 or newer. From a clone of this repository:

```sh
python -m venv .venv
```

Activate it with `.venv\Scripts\Activate.ps1` in PowerShell or `source .venv/bin/activate` on Linux/macOS, then:

```sh
python -m pip install -e ".[dev]"
python scripts/verify.py
```

No particular editor, agent integration, Java installation or Minecraft download is required for the normal Python checks. Tests create disposable fixtures and use no model API. Java and Minecraft are needed only for a change that actually requires game/build validation.

## Find the right place

| Location | Responsibility |
| --- | --- |
| `src/minecode_runtime/` | MCP server, project inspection, retrieval, diagnostics and host installation |
| `skills/` | Six skills and supporting Markdown references |
| `references/sources/` | Authoritative source and developer-document registries |
| `references/gameplay/` | Attributed Minecraft terminology reference |
| `integrations/` | Metadata for separately installed optional providers |
| `tests/` | Offline unit, contract and deterministic Minecraft evidence regressions |
| `scripts/` | Verification, documentation links and installed-package acceptance |
| `release_resources.py`, `MANIFEST.in` | Explicit distribution resource lists |

Read the [architecture](docs/ARCHITECTURE.md) before changing a boundary. The host owns general coding, Git and host permissions; MineCode should add Minecraft-specific value.

## Make a focused change

Open a branch and describe the concrete problem, reproduction and expected behavior. Prefer a small fix over a new abstraction. Discuss substantial features before implementing them; don't add a tool merely because another API is available.

- **Skills:** preserve discoverable `name`/`description` front matter, scope guidance to the right task, and keep references relative and portable. Don't require private helpers. Update installer/packaging lists if a resource genuinely changes.
- **MCP behavior:** follow existing typed contracts and annotations. Preserve actionable errors, bounded output and explicit permission opt-ins. Add a regression for a reproduced defect; don't create a second test runner or require paid models.
- **Minecraft evidence:** pin the version and mappings. Use independently checked expected answers, not output generated by the implementation under test. Keep provenance, unknowns and licensing information intact. A build alone does not establish gameplay behavior.
- **References:** edit authoritative registries, record origins and applicable licenses, and distinguish reference metadata from permission to copy code. See [retrieval](docs/RETRIEVAL.md) and [licensing](docs/LICENSING.md).

## Check your work

Run relevant tests during development. Before submitting, use the existing CI checks:

```sh
ruff check src tests scripts
ruff format --check scripts
basedpyright
python scripts/verify.py --full
python scripts/check_docs.py
```

The short verification covers MCP contracts, skills, installation and selected pinned evidence regressions. `--full` runs the complete unittest suite. Neither starts a paid agent evaluation or downloads Minecraft. Some filesystem checks skip where the OS doesn't permit the operation; inspect reported skips.

For a runtime or packaging change, build from a **clean checkout**:

```sh
python -m build
```

This builds a wheel through a source distribution. Install the wheel into a separate environment, change to a directory outside the checkout, and run its Python with `-I` against `scripts/check_installation.py` in the checkout. Windows and Linux examples are in `.github/workflows/quality.yml`. Acceptance checks the installed CLI, 14 interfaces, six skills, links and setup/removal behavior for both host formats. It doesn't start a model or prove a live coding host has loaded its tools.

Stale build files are deliberately rejected. Use a fresh clone or a separate clean build directory rather than packaging old outputs. See [installation](docs/INSTALLATION.md) for installing a reviewed wheel and restarting the host connection.

## Submit and share responsibly

Explain what changed, why, what you checked and any material limits. Keep pull requests reviewable. Don't include local agent state, generated projects, caches, downloaded game JARs, personal paths, credentials or conversation logs. Sanitize reproductions before sharing them; follow the [security policy](SECURITY.md) for sensitive security details.

Your original contributions use MineCode's MIT license. Retain third-party notices and confirm that you have the right to contribute external material. The community values in the README don't add license restrictions. Forks can choose their own direction while preserving required notices.
